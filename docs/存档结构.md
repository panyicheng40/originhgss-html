# 起源心金 4.03 存档结构（实测版）

本文全部结论来自：同一存档两个时间点的逐字节对比、ROM 内 `item_data.narc` 的解析、以及 [Project Pokémon 的 HGSS 存档结构](https://projectpokemon.org/docs/gen-4/hgss-save-structure-r76/) 的交叉印证。

## 一、文件总体布局

`.sav` 固定 512 KiB，由**两份完全独立的副本**组成，每份 256 KiB：

```
0x00000 ┌ 副本 A ─────────────────────────────┐
        │ General 数据      0x00000..0x0F7BB  │ CRC 覆盖
        │ General 尾部      0x0F7BC..0x0F7CB  │
        │   0xF7BC u32 存档计数器             │
        │   0xF7C0 u32 区块大小 = 0x0F7CC     │
        │   0xF7C4 u32 常量 0x20060623        │
        │   0xF7C8 u16 0                      │
        │   0xF7CA u16 General CRC-16/CCITT   │
        │ 填充              0x0F7CC..0x0F7FF  │ 全 0xFF
        │ Storage 数据      0x0F800..0x27BF7  │ CRC 覆盖
        │ Storage 尾部      0x27BF8..0x27C07  │
        │   0x27BF8 u32 存档计数器（与 General 相同）
        │   0x27BFC u32 区块大小 = 0x18408    │
        │   0x27C00 u32 常量 0x20060623       │
        │   0x27C04 u16 1                     │
        │   0x27C06 u16 Storage CRC-16/CCITT  │
        │ 填充              0x27C08..0x3FFFF  │ 全 0xFF
0x40000 └ 副本 B（结构完全相同）───────────────┘
```

- **CRC 算法**：CRC-16/CCITT，初值 `0xFFFF`，多项式 `0x1021`，不反射。
- General CRC 覆盖 `[0x0000, 0x0F7BC)`；Storage CRC 覆盖 `[0x0F800, 0x27BF8)`。
- 尾部与填充区**不在校验范围内**，但也不要写：写错会让游戏读到不一致的块信息。

## 二、游戏读哪一份：看计数器

两份副本各有一个 u32 计数器（`0xF7BC` 与 `0x27BF8`，同一副本内两者相等）。**游戏读取计数器较大的那一份**，这也是所谓“双槽轮换”：每次存档写到较旧的那一份并 +1。

实测证据（同一玩家的两个时间点存档）：

| 文件 | 副本 A 计数 | 副本 B 计数 | 游戏实际读取 |
|---|---:|---:|---|
| `起源心金4.03正式版.sav` | 50 | 49 | A（较新） |
| `起源心金4.03正式版1.sav` | 50 | 51 | B（较新） |

两份文件的差异**全部集中在副本 B**，副本 A 逐字节相同；同时金额从 `968,831` 变成 `973,119`、部分地图/记录标志变化。这直接证明：新状态写进了 B，而 A 停留在第 50 次存档。

**这就是最容易出事的地方**：如果编辑器固定读 A、又同时写两份，那么在“B 是当前存档”的文件上（上表第二个），你会看到并修改到**旧状态**，还会把旧状态覆盖回 B。

## 三、General 区块内部

| 偏移 | 内容 |
|---|---|
| `0x74` | 训练家 ID（u16） |
| `0x76` | 里 ID（u16） |
| `0x78` | 金钱（u32） |
| `0x94` | 队伍数量（u32，0–6） |
| `0x98` | 队伍槽 ×6，每槽 **236 字节** = 136 字节宝可梦记录 + 100 字节队伍缓存（当前 HP、六项能力、等级等） |
| `0x620..0x643` | 保留区（恒为 0，勿写） |
| `0x644` | **背包**（8 个口袋，紧凑数组，见下） |
| `0xF7BC` | 区块尾部（计数器等） |

## 四、背包口袋（实测表）

| 口袋 | 起点 | 格数 | 存档内顺序 |
|---|---:|---:|---:|
| 普通道具 | `0x644` | 165 | 1 |
| 重要物品 | `0x8D8` | 50 | 8 |
| 秘传机（招式机/秘传机） | `0x9A0` | 163 | 4 |
| 回复药品 | `0xC2C` | 40 | 2 |
| 树果 | `0xCCC` | 64 | 5 |
| 精灵球 | `0xDCC` | 24 | 3 |
| 战斗道具 | `0xE2C` | 13 | 7 |
| 邮件 | `0xE60` | 12 | 6 |

每条 4 字节：`u16 道具 ID` + `u16 数量`。

**两条硬规则**（违反就是坏档）：

1. **紧凑无空洞**。条目从第 0 格连续排列，后面全 0。中间出现 0，游戏会认为口袋到此结束——这就是上一轮“普通道具整页清空”的直接原因。
2. **秘传机口袋按道具 ID 升序**。游戏自己会排序，编辑器写入后也要排。

## 五、Storage 区块内部

| 偏移 | 内容 |
|---|---|
| `0xF800` | PC 盒子：24 盒 × `0x1000` 字节 |
| 每盒 | 30 格 × 136 字节 = `0xFF0`，盒尾 `0x10` 字节为盒子元数据 |
| `0x27800..0x27BF7` | Storage 尾部扩展区（约 158 字节有效数据，用途未确认，**不要写**） |
| `0x27BF8` | 区块尾部 |

## 六、宝可梦记录（136 字节）

```
0x00 u32 PID
0x04 u16 标志位（蛋 / 昵称等）
0x06 u16 校验和
0x08..0x87 加密主体 128 字节
```

- 加密：第四世代 LCG，`seed = 校验和`，常数 `0x41C64E6D` / `0x6073`，每 2 字节异或一次。
- 块序：按 `(PID & 0x3E000) >> 13` 取 24 种块顺序之一重排四个 32 字节块。
- 校验和：解密并按块序还原后，128 字节按 u16 累加。
- 队伍槽的前 136 字节就是这条记录，后 100 字节是队伍缓存（`0x88` 当前 HP、`0x8A` 起六项能力、`0x96` 等级）。

实测：存档里全部 55 条记录（6 队伍 + 49 盒子）做“解码→重新编码”，**逐字节完全一致**；修改后再编码，校验和自洽、PID 与标志位保持不变。

## 七、编辑器现在的写入规则

1. **只改游戏会读取的那份副本**（计数器较大者），另一份保持原样。写入前会在诊断页显示“当前编辑副本 / 计数器”。
2. **口袋整体重排**：删除=前移，新增=紧凑插入（秘传机自动排序），不再只清零单格。
3. **导出前四道检查**，任一不过就中止导出并说明原因：
   - 重算两份副本的区块 CRC；
   - 复核 CRC；
   - 结构体检（队伍数量、队伍与盒子记录校验和、八个口袋的紧凑性）；
   - 越界白名单（本次改动只要落在“队伍槽 / 盒子槽 / 口袋 / 队伍计数 / CRC”之外，直接拒绝）。
4. 未知道具 ID（不在内置道具表内）拒绝写入。

## 八、禁区清单

以下区域编辑器永不写入，若将来扩展功能也需要避开：

- `0x0F7CC..0x0F7FF`、`0x27C08..0x3FFFF`：全 `0xFF` 填充；
- 区块尾部 14 字节（`0x0F7BC`、`0x27BF8` 起）：计数器/大小/常量；
- `0x620..0x643`：保留区；
- `0x27800..0x27BF7`：Storage 尾部扩展区；
- 每盒末尾 16 字节元数据。
