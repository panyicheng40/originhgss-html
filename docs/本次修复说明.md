## 二、`？？？` 到底是怎么回事

共 23 个 ID 的名称是 `？？？`：`113`、`115`–`134`、`428`、`429`。

对 23 个图标的 PNG 做哈希比对：

- **22 个共用同一张图**（同一 SHA-1），就是截图里那个通用“?”图标 → 纯粹的未启用占位槽；
- **只有 `#429` 有独立图标**（头盔状美术），名称仍是 `？？？`。

结论：**名称才是“这个道具是否启用”的权威信号**。图标库对所有 ID 都排了一张图，未启用槽位大多数用通用“?”，个别残留了旧美术——多半是改版删改道具时留下的孤儿资源。所以“有图标”不能证明道具存在，`#429` 仍然应当视为未启用。

处理方式：这 23 个 ID 从“添加道具”列表里全部剔除；如果某个存档里已经存在这些 ID，列表里照常显示，不会破坏存档。

## 六、第二轮：导出后存档损坏（严重）+ 页签顺序

### 1. 事故现象

只在编辑器里删了“普通道具”第一行（心之鳞片），导出后进游戏：名称消失、数量还在，普通道具整页清空，无法正常游戏。

### 2. 逐字节对比

原存档与导出存档逐字节比较，全文件只差 8 个字节：

| 位置 | 原值 | 导出值 | 含义 |
|---|---|---|---|
| `0x644` | `5D` | `00` | 心之鳞片 ID 93 → 0 |
| `0x646` | `60` | `00` | 数量 96 → 0 |
| `0xF7CA` | `8BFB` | `7054` | General CRC（重算） |
| `0x40644`/`0x40646`/`0x4F7CA` | — | — | 第二份副本的同样修改 |

也就是说编辑器并没有“清空”背包，只把一格清零、并正确重算了 CRC（两份副本的 CRC 都验证自洽）。问题出在**清零的位置和方式**。

### 3. 根因一：三个口袋的起点提前了 5 格

对照 [Project Pokémon 的 HGSS 存档结构](https://projectpokemon.org/docs/gen-4/hgss-save-structure-r76/) 并用你的存档实测，真实布局是：

| 口袋 | 真实起点 | 格数 |
|---|---:|---:|
| 普通道具 | `0x644` | 165 |
| 重要物品 | `0x8D8` | 50 |
| 秘传机（招式机/秘传机） | `0x9A0` | 163 |
| 回复药品 | `0xC2C` | 40 |
| 树果 | `0xCCC` | 64 |
| 精灵球 | `0xDCC` | 24 |
| 战斗道具 | `0xE2C` | 13 |
| 邮件 | `0xE60` | 12 |

原编辑器用的是 `0x630` / `0x8C4` / `0x98C`——**正好都早了 5 格（20 字节）**。原先“读出来看着没问题”，是因为从早了 5 格的地址开始读，前 5 格恰好是 0，列表里被跳过，看起来和从 `0x644` 读一模一样；但写入时下标就整体偏了 5 格。

### 4. 根因二：删除只把格子清零，口袋没有前移

游戏把每个口袋当作**紧凑数组**：条目从第 0 格连续排布，后面全是 0。用真实偏移读原存档，八个口袋全部满足这个规则（无任何中间空洞），秘传机口袋还严格按道具 ID 升序——反过来印证了这一点。

原实现删除时只把那一格写成 0，于是第 0 格变成了空洞。游戏从第 0 格开始读，读到 0 就认为口袋结束，于是“普通道具整页清空”；残留的错乱显示是游戏在下标越界后读到的脏数据。

### 5. 修复内容

1. **口袋表改成真实偏移与格数**，并按游戏内页签顺序排列：普通道具 → 回复药品 → 精灵球 → 秘传机 → 树果 → 邮件 → 战斗道具 → 重要物品。
2. **新增紧凑读写层**：`pocketItemList()` / `writePocketList()` 统一按“读到第一个 0 为止”读取、整体重写。
3. **删除改为整体前移**（`removePocketSlot`），不再留空洞。
4. **新增道具改为紧凑插入**，秘传机口袋写入后自动按 ID 升序排序（与游戏行为一致）。
5. **列表行号改用紧凑下标**，避免载入带空洞的旧存档时删错项。
6. 数量框写回同样走紧凑列表；把数量改成 0 等于删除该条。

### 6. 修复存档

`起源心金4.03正式版_已修复.sav` 已生成（桌面），做法是：以 `RAW/起源心金4.03正式版.sav` 为基准，按正确方式删除心之鳞片（整体前移），重算两份副本的 General CRC。校验结果：

```

所有口袋 holes_after=0，两份副本 CRC 均 OK
```

### 7. 验证

用 Node + 最小 DOM 壳加载改后的页面，喂入修复后的存档：八个口袋的项数与偏移完全对应；删除第 0 行后列表从 63 变 62 且无空洞；重新添加会追加到末尾；向秘传机口袋加入 ID 500 后列表仍严格升序。页面两个 script 块语法检查通过。

## 七、第三轮：结构加固，杜绝再次坏档

完整结构已单独整理在 [存档结构.md](存档结构.md)。这一轮修掉两个**尚未爆发的隐患**，并加了四道导出前检查。

### 1. 隐患一：编辑器永远读 A 副本

存档是两份 256 KiB 副本轮换，游戏只读取计数器较大的一份。实测你的两个存档：一个当前是 A（计数 50 vs 49），另一个当前是 B（50 vs 51）。而编辑器固定读 A、并且同时写两份——在第二种文件上，你会看到旧状态，改完还会把旧状态覆盖回当前存档，属于静默的数据回退。

**处理**：载入时比较两份副本的计数器，确定游戏实际读取的那一份；所有浏览与修改都只针对它，另一份保持原样。诊断页会显示“当前编辑副本”和 A/B 计数器。

### 2. 隐患二：写入面过大

原先每次修改都同时写两份副本。现在只写活动副本，写入面直接减半；未改动的副本连 CRC 都不动（其校验仍自洽）。

### 3. 新增四道导出前检查

`updateSaveChecksums()` → `validateSaveChecksums()` → `auditActiveSave()` → `checkWriteScope()`，任一不过就中止导出并弹窗说明：

| 检查 | 内容 |
|---|---|
| CRC 重算与复核 | 两份副本的 General / Storage |
| 结构体检 | 队伍数量 ≤6、队伍与 720 个盒子槽的记录校验和、八个口袋必须紧凑（中间出现空位即报错） |
| 越界白名单 | 与原始文件逐字节比对，改动必须落在队伍槽/盒子槽/口袋/队伍计数/CRC 之内，否则拒绝 |
| 道具 ID 校验 | 不在内置道具表里的 ID 直接拒绝写入 |

顺带修正一处误报：体检在“有未导出修改”时不再提示 CRC 不符（CRC 本来就要等导出时重算），只有载入即损坏才会报。

### 4. 验证结果

用 Node + 最小 DOM 壳加载改后页面，喂入 `起源心金4.03正式版1.sav`（当前副本为 B）：

- 正确识别 `ACTIVE = 0x40000`（B），计数器 A=50 / B=51；
- 删除普通道具第 0 项后：副本 A 变动 **0 字节**，副本 B 变动 104 字节，列表 63→62 且无空洞；
- 导出文件两份副本 CRC 全部自洽，副本 A 与原始逐字节一致；
- 故意在 `0x41000`（结构外）写一个字节 → 导出被拒绝，提示“检测到已知结构之外的写入：0x41000”；
- 用上一轮的坏档测试 → 体检报“普通道具 中间出现空位（第 2 格）”，导出被拒绝；
- 全部 55 条宝可梦记录（6 队伍 + 49 盒子）解码后重新编码，逐字节一致；改属性后再编码，校验和有效、PID 与标志位不变。


## 八、第四轮：口袋隔离失效与道具区界面

### 1. 为什么顽皮薄荷能加进普通道具

“已选道具”只保存在 `itemId` 输入框和预览区里，**切换口袋时完全没有清理**；写入时也只检查“道具表里有没有这个 ID”，不检查它属于哪个口袋。于是：在回复药品里选中顽皮薄荷 → 切到普通道具 → 直接点“增加”就写进去了。

### 2. 修复

1. **切换口袋即清空已选**：`clearChosenItem()` 会清空 ID 输入与预览，切页签、打开存档、页面初始化时都会调用。
2. **写入前强校验归属**：`addItem()` 里比对 `itemCategory(id)` 与当前口袋 key，不一致直接拒绝并提示“「顽皮薄荷」属于「回复药品」，不能放进「普通道具」”。
3. **顺带修掉一个同类隐患**：树果选择器原来输出的是“树果序号”（1–60），而存档里存的是全局道具 ID（149–208），点选树果会写进错误的道具 ID。现已改为 `序号 + 148`。

### 3. 界面调整

- **已选道具改为卡片**：图标 42px + 名称 + `ID` 胶囊 + 描述，右侧一个圆形“×”取消按钮；未选择时显示虚线空态提示，不再是原来那行裸文本。
- **列表行对齐**：行内改成三列（信息 / 数量 / 删除），图标固定 40px 不缩放、不参与压缩，文字块 `min-width:0`，名称、描述、ID/格位分层显示；删掉了原来重复的“数量”小标题。
- **按钮宽度**：“打开道具列表”不再拉满整行，改为常规宽度。

### 4. 验证

- 选中顽皮薄荷后切到普通道具：`itemId` 变空、预览回到空态；
- 强行写入顽皮薄荷到普通道具：被拒绝，列表数量不变；
- 在回复药品里写入同一道具：正常，23 → 24；
- 树果选择器前三个卡片 ID 显示为 `#149 / #150 / #151`（全局 ID）；
- 列表行结构包含 `item-main`、`item-text`、`qty-cell`，图标与文字同一行居中。

## 十三、清空口袋 / 一键添加 的安全性加固

### 1. 结构前提

每个口袋是**固定长度数组**（如普通道具 165 格），没有独立的“数量”字段；游戏从第 0 格开始读，读到第一个 `id=0` 就结束。因此：

- 只要列表保持**紧凑**（前 n 格有效、第 n 格起为 0），就一定是合法后备；
- 口袋后面的空区域即使有残留数据，游戏也不会读。

### 2. 改动前的两个隐患

| 操作 | 原实现 | 风险 |
|---|---|---|
| 清空口袋 | `raw.fill(0, start, start+slots*4)` 把整段容量填 0 | 会覆盖口袋尾部“未使用但可能被游戏占用”的区域 |
| 任意写入 | `writePocketList` 把剩余空间整片清零 | 同上 |

### 3. 现在的做法：最小写入

- `writePocketList(base,p,list,oldLen)` 只写 **新列表的格子**，并把 `[新长度, 旧长度)` 这段清零；**不再碰**口袋剩余空间；
- 清空口袋 = 只清零“当前实际占用的 n 格”，其余原样保留；
- 一键添加 = 只补缺失的招式机、写 1 份、按 ID 排序，容量不足时提示并停止；
- 两个操作都只写**活动副本**；清空后校验和暂不更新，导出时统一重算。

### 4. 验证结果

逐个口袋清空（8 个口袋轮测）：

```
招式机   137 项 → 0 项 · 口袋内改动 411 字节 · 口袋外改动 0 字节
树果      11 项 → 0 项 · 口袋内改动  22 字节 · 口袋外改动 0 字节
战斗道具   2 项 → 0 项 · 口袋内改动   4 字节 · 口袋外改动 0 字节
重要物品  16 项 → 0 项 · 口袋内改动  48 字节 · 口袋外改动 0 字节
邮件       0 项 → 直接提示“已经是空的”，不写入
```

一键添加：

```
137 → 138 项 · 严格升序 · 新增项数量均为 1 · 结构体检通过 · 越界写入 0
清空后再一键添加：0 → 138 项 · 结构体检通过 · 越界写入 0
导出：两份副本 CRC 均正确 · 导出后招式机口袋 138 项 · 无告警
```

再加上导出前的四道检查（CRC 重算与复核、结构体检、越界白名单、道具 ID 校验），即使将来某个操作写错，也**不会生成坏档**。


## 十四、浮层层级与遮挡问题

### 1. 现象

- 同类问题一并处理：编辑弹窗里的下拉搜索列表在底部空间不足时会**向上展开**（`.search-select.drop-up`），避免被滚动容器裁切。

### 4. 验证

### 补充：手机端道具行第二排布局

上一版把「数量」放左、「删除」贴最右，中间空出一大截。现在把两者包进 `.item-controls`：
